# Intent

## Background

Agent Tunnel is built to solve a specific problem on user demand:
They want to access their private network without having Gateway sitting in their private network.
The Agent Tunnel feature would allow each agent to make outbound connections to a publicly accessible Gateway which is also accessible from all the clients. 
Benefits this gives:
1. One Gateway can now guide traffic to multiple private networks without having to be in those networks.
2. You don't have to pay Ngrok or Cloudflare to expose your private network to the public internet; you have a Gateway on the edge directly.

## Considerations

With this intent, we would also allow users to manage their agents, which includes creating, deleting, and listing agents. 

Gateway should have a persistent layer to store the agent information. Previously it was stateless, which introduced challenges to the "delete" semantics: once we delete an agent from memory and Gateway restarts, we would have no way to know if that agent was deleted before or not, since right now it is stateless.

## Technical Background

#### Enrollment Process
1. Administrators must generate an enrollment token via the provisioner and copy the enrollment token to the agent installer or the agent binary.
2. After the agent obtains the enrollment token, the agent will generate 
    a. a UUID 
    b. a public/private key pair (the public key is later sent together as part of the CSR while the private key is kept in the agent)
    c. a CSR (Certificate Signing Request) 
    and send the enrollment token and CSR to Gateway.
3. Gateway will verify the enrollment token and sign the CSR, then return the signed certificate to the agent. 
4. Then, the agent will use the signed certificate to establish a secure connection with Gateway.

Note: the CA is self-signed and generated by Gateway. 

## Intents

1. We should have a stable persistent layer to record what agents we currently recognize. We should not have Gateway send a delete request to an agent and ask the agent to delete its certificate; Gateway should dictate the recognition of agents.

2. We should persist the enrollment jti, the client SPKI sha256, the agent id (a UUID generated by the agent), and the name of the agent.
    - Enrollment jti is used to prevent replay attacks
    - Client SPKI sha256 is used for binding an accepted Agent identity to its authorized public key.
    - Agent id and name are used to identify the agent and for human-readable purposes.
    - Agent id and name are unique; names are case-insensitive

3. All the subnet/domain advertisement information is kept in memory and sent by the agent immediately after connection or reconnection, or later in periodic RouteAdvertisement refreshes.

4. Rule of thumb: if an administrator deletes an agent, then the agent should remain rejected unless given a new enrollment token with a newly generated key.

5. Gateway should accept an Agent connection if and only if all three conditions are met:
    - Agent's certificate is valid (signed by the Gateway CA and not expired)
    - Agent ID matches the subject alternative name in the certificate and the id matches the one in Gateway's agent db together with the same SPKI sha256 (see below)
    - The SPKI sha256 of the agent's public key matches the one in Gateway's persistent layer

6. The semantics of delete
    - The persisted record of the agent MUST be removed
    - All open connections from the agent MUST be closed
    - All re-connections from the same agent MUST be rejected
