## Background
Agent Tunnel is built to solve a specific problem on user demand:
They want to access their private network without having Gateway sitting in their private network.
The Agent Tunnel feature would allow each agent to make outbound connections to a publicly accessible Gateway which is also accessible from all the clients. 
Benefits this gives:
1. One Gateway can now guide traffic to multiple private networks without having to be in those networks.
2. Third party tunelling services will no longer be necessary if user choose to host Gateway publicly.

## Terminology
- Persistent layer: really just a sqlite/turso database 
- Agent: The Devolutions Agent that surves many different purposes, including tunneling traffic from users internal network to Gateway, for this INTENT.md, we will only discuss the tunneling part
- Enrollment token: a token generated by the provisioner used to enroll an agent.

## Considerations

The agent registration or deletion state of agents must survive Gateway restarts.

## Technical Background

### Enrollment Process (simplified)
1. Administrators must generate an enrollment token via the provisioner and copy the enrollment token to the agent installer or the agent binary.
2. After the agent obtains the enrollment token, the agent will generate 
    a. a UUID 
    b. a public/private key pair (the public key is later sent together as part of the CSR while the private key is kept in the agent)
    c. a CSR (Certificate Signing Request) 
    and send the enrollment token and CSR to Gateway.
3. Gateway will verify the enrollment token and sign the CSR, then return the signed certificate to the agent. 
4. Then, the agent will use the signed certificate to establish a secure connection with Gateway.

Note: the CA is self-signed and generated by Gateway. 

## Invariants
    - An agent is registered if and only if there is a corresponding record in the persistent layer.
    - An deleted agent must not be able to reconnect unless a new enrollment token is provided.
    - Gateway must only accept Agent connection if and only if all three of these conditions are met
        1. Agent's certificate is valid (signed by the Gateway CA and not expired)
        2. Agent ID matches the subject alternative name in the certificate and the id matches the one in Gateway's agent db together with the same SPKI sha256 (see below)
        3. The SPKI sha256 of the agent's public key matches the one in Gateway's persistent layer

## Note:

1. We should persist the enrollment jti, the client SPKI sha256, the agent id (a UUID generated by the agent), and the name of the agent.
    - Enrollment jti is used to prevent replay attacks
    - Client SPKI sha256 is used for binding an accepted Agent identity to its authorized public key.
    - Agent id and name are used to identify the agent and for human-readable purposes.
    - Agent id and name are unique; names are case-insensitive

2. All the subnet/domain advertisement information is kept in memory and sent by the agent immediately after connection or reconnection, or later in periodic RouteAdvertisement refreshes.
