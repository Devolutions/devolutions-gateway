- The shared vectors' pass rule is in `docs/agent-identity/INTENT.agent-identity.md`, "Conformance": a signer passes when it reproduces a vector's inputs and its signature verifies under the vector's public key.
- `docs/agent-identity/verify_vectors.py` recomputes the shared vectors with an implementation-independent library.
- `a_renewal_happy_path`, `a_request_renewal_connected`, `a_request_renewal_while_offline`, `a_multi_authority` and `a_rotation_migrates_connected_agent` need leaves of at least 3/2 of a test's timeout, so that none of their certificates comes due for renewal ("Schedules" in the agent's intent) or expires (§7.4) before the test ends, and only a requested renewal or a rotation replaces one; on an authority with shorter leaves they report `SKIP` rather than excuse a closed channel or a later certificate.
- Verified by review only: the randomness of secrets, nonces and challenges, and the stability of `authority_id` across restores.
- Verified by review only, because the suite reads neither the Windows event log nor the agent's warnings: system event 1100 for an unavailable key storage and for a required policy without an available storage (`devolutions-agent/src/identity/INTENT.md`), and the warning for a malformed policy (`crates/agent-identity/INTENT.md`, "Key storage").
- On Windows the key storage cases cover both the Windows software provider and the file backend; the cases that need both report `N/A` elsewhere, where the suite knows of only one available key storage.
- Known gaps, with no test yet:
  - a held renewal that starts once a listed key storage becomes available (§5.7), and the agent checking an unavailable storage again on each pending-directory poll ("Identities" in `crates/agent-identity/INTENT.md`), because the suite cannot make a storage unavailable to the agent and then available again;
  - the timing of a renewal for a required policy that excludes the current key's storage (§5.7): after a renewal in progress, within 15 minutes, and not sooner than 10 minutes after the last one, because the cases turn the jitter and the wait between renewals off;
  - a renewal that a `certificate_expired` refusal (§5.4) or pending-key recovery (§8.1) starts while a required policy holds renewals back, and the key of a pending-key recovery following the policy;
  - `tpm` as an available or unavailable key storage, because the suite has no independent knowledge of a TPM on the machine, so the cases name an unlisted storage where they need an unavailable one;
  - `key_storage_available` omitted when no key storage is available (§3.1), which never holds for an agent that holds a key;
  - a policy object with members beyond `backends` and `required` (§5.7), whose treatment the contract leaves open;
  - product-specific config fields avoiding the `key_storage` name (§5.2), an authority-side rule with no wire behaviour of its own; the mock's config control does not merge that name;
  - the §1 conventions beyond the error body, timestamps, repeated members, nesting depth, invalid Unicode and canonical `base64`;
  - a renew or check-in body whose metadata holds a control character or an invisible format character (§3), which `p_metadata_limits` and `p_metadata_invisible_format_characters` send only at enrollment and `p_channel_hello_invalid_metadata_rejected` only in `Hello`;
  - a code point inside a listed range of §3 other than the six that `p_metadata_invisible_format_characters` and `a_metadata_invisible_format_characters_removed` send;
  - the `machine_id` value on Windows and macOS (§3.1), which the metadata check does not compare, because the suite has no independent reading of the SMBIOS UUID or `IOPlatformUUID`, and on a Linux host whose `/etc/machine-id` the suite cannot read for a reason other than its absence;
  - the agent's removal of C0, DEL and C1 control characters (§3.1), and its removal of invisible format characters at renew, check-in and `Hello`, because no test sets such a value in the metadata override before those sends;
  - an `agent_channel_url` holding an `@`, which the agent treats as absent (§5.2, §7.2), because no mock fault delivers such a URL;
  - the shape of the agent's own CSR (§4: one attribute, an `extensionRequest` holding only the enrollment URL extension) and the URL its renewal CSR names, because the mock reports no CSR it received; the mock accepting the agent's enrollments shows only that their CSRs name the token's `u` where the mock reads it;
  - the agent's check of an enrollment that returns a known authority ID from another base URL ("Pending-enrollment files" in `crates/agent-identity/INTENT.md`), such as a chain through a P-384 CA accepted and an RSA-signed chain refused with `authority_conflict`, because a mock serves one base URL and issues only from its own root.

The suite's tests of each party's own intent:

- DVLS's management API (DVLS's Agent Identity intent, `DVLS/Server/server/Common/AgentIdentity/INTENT.md` in the RDM repository, and DVLS's OpenAPI document), reached only through the suite's DVLS module: `p_management_tokens_crud_and_states`, `p_token_expiry_default_and_maximum`, `p_management_requires_auth`, `p_management_permission_denied`, `p_rotation_start_requires_auth`, `p_rotation_without_root_conflicts`, `p_root_key_unavailable_conflicts`, `p_listing_pagination_stable_during_concurrent_enrollment`, `p_listing_views_filters_and_bounds`, `p_identity_statuses`, `p_settings_read`, `p_settings_change_bounds`, `p_settings_certificate_lifetime_applies_to_new_certificates`, `p_settings_channel_switch_withdraws_and_restores_channel_url`.
  On DVLS, `p_config_hello_reconciles_stale_revision` makes an identity's revision stale by switching the agent channel off and on, the only config change that DVLS's intent gives its management API ("Certificates and channel").
- DVLS's login (DVLS's public OpenAPI document), with which the DVLS module opens sessions for the application identities that `--app-key`, `--second-app-key` and `--unprivileged-app-key` name: the module's unit tests check that a refused session logs in again and retries its request only once, and that a session logs in again before it reaches the age of a refused one; a full run outlasts DVLS's 7-minute session lifetime.
- Friendly names (shared intent, "Enrollment"): `p_friendly_name_format`, `p_friendly_name_white_space_and_truncation`.
- The agent's local behaviour (`crates/agent-identity/INTENT.md`):
  - "Identities", a key recorded in a key storage that isn't available, or under a well-formed name the agent doesn't know, leaves its identity or pending file unused and unchanged, with an error-level log line: `a_current_key_in_unavailable_storage_pauses_only_its_identity`, `a_pending_key_in_unavailable_storage_pauses_until_restored`, `a_in_progress_key_in_unavailable_storage_waits`.
    The harness test `error_log_level_is_distinct_from_message_text` pins how they find an error-level line, with and without colour codes.
    A current key's record cannot be restored after the pause, since start-up deletes the key that its record no longer names with its storage, so only the pending-key and in-progress cases restore their record.
  - "Key storage", every key created without a policy, and every enrollment key, is in the built-in default: the stored-identity check of every agent test that enrolls, and `a_key_storage_enrollment_key_in_builtin_default`.
  - "Local state", an `identity.json` or in-progress record without a well-formed `key_storage` stops all identity processing and is never repaired: `a_identity_file_without_key_storage_stops_identity_processing`, `a_in_progress_record_without_key_storage_stops_identity_processing`.
    The audit after each agent test requires a well-formed `key_storage` in every slot and in-progress record, which the harness test `orphan_audit_accepts_both_records_and_cleanup_is_prefix_scoped` pins.
  - "Stored identities", start-up deletes every key with the agent's prefix that no record names with its key storage: `a_start_deletes_unrecorded_keys_in_every_available_storage`.
  - "Pending-enrollment files", the last of two tokens for one authority to complete wins: `a_two_pending_tokens_same_authority_last_wins`.
  - "Pending-enrollment files", each success deletes its pending file and in-progress record; these tests wait for both deletions after the identity is stored: `a_enroll_lost_response_retried_across_restart`, `a_two_pending_tokens_same_authority_last_wins`, `a_two_pending_tokens_different_authorities_progress_independently`.
  - "Schedules", a renewal starts no sooner than the wait after the identity's previous renewal completed, and a renewal the authority requests during the wait still starts once it ends: `a_renewal_waits_between_renewals`, with the wait shortened to 15 seconds through `min_renewal_interval_secs` (`devolutions-agent/src/identity/INTENT.md`, "Configuration") and the authority's request pushed on the channel at least 4 seconds before the wait ends.
    Before the second request, the agent must hold one connected stream with no further authenticated connect for 1.5 seconds.
    The test measures from the later of the moment before the first renewal request and the last poll of the mock's requests that showed no confirm, since the agent completes the renewal after its confirm arrives.
    It requires the next renew no sooner than the wait after that and within the wait plus 10 seconds after the second request, and, in the mock's event order after the second request, no `stream_opened`, `stream_authenticated` or `check_in_received` before the first `renew_received`, so that only the pushed request can have triggered it.
    Once that renewal settles, it requires the agent's `Ack` of the request within the suite's usual 20-second wait.
    The 10-minute wait itself, the wait after a schedule or a `certificate_expired` refusal (§5.4), and the exemption of `renewal_after_secs` are not checked.
  - "Stored identities", a renewal ends with the new key current, no pending or previous key, and the old key deleted; these tests wait for that state before they stop the agent: `a_renew_transient_failures_retry_without_state_change`, `a_renewal_lost_response_retried`, `a_renewal_waits_between_renewals`, `a_confirm_barrier_blocks_channelless_traffic`, `a_confirm_expired_pending_renews_with_fresh_key`, `a_expired_current_renews_in_grace_or_rejects_beyond`, `a_make_before_break_on_renewal`, `a_request_renewal_connected`, `a_request_renewal_while_offline`, `a_request_renewal_without_channel`, `a_rotation_migrates_connected_agent`, `a_rotation_migrates_through_check_in`.
    `a_renewal_happy_path` restarts the agent without `renewal_after_secs`, so that the restarted agent keeps its renewed key.
  - "Stored identities", writes are atomic: the audit after each agent test parses each stored `identity.json` and each tracked in-progress record, and tolerates a temporary sibling of either, because stopping the agent can cut a write short and the intent promises atomicity, not the removal of that file.
    The harness test `orphan_audit_accepts_both_records_and_cleanup_is_prefix_scoped` pins that the audit tolerates such a file, still rejects one holding a private key, and still rejects a temporary sibling of a pending or key file.
- Device keys (`crates/device-key/INTENT.md`, "Operations"), no leftover copy of a private key survives a later operation in the same key store: `a_request_renewal_without_channel` checks it after a restart.
  The audit after each agent test tolerates a leftover copy of a deleted key, because stopping the agent can follow its last key-store operation.
  The harness test `orphan_audit_accepts_both_records_and_cleanup_is_prefix_scoped` pins that the audit tolerates such a copy, still rejects a leftover copy of a recorded key, and that the post-operation check reports it.
